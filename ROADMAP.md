# ROADMAP.md

## Цель
Стабилизировать связь с ESP32, перепроектировать протокол подключения/команд и перевести клиент на React Native Expo без потери текущего UX «настроек телефона».

## Фаза 0. Аудит и фиксация базовой версии
- Зафиксировать текущий функционал (видео/чеклист): connect, отправка текста, stop, автостоп по таймеру.
- Описать фактический BLE контракт (текущая строка-команда, ожидаемые статусы).
- Добавить минимальный диагностический лог в app и firmware (время, событие, код ошибки).

Критерий готовности:
- Есть документ с текущим протоколом и списком воспроизводимых багов.

## Фаза 1. Быстрая стабилизация текущего стека (Web + ESP32)
- Исправить критичные ошибки прошивки:
  - пропущенная `;` у `addDescriptor`
  - проверка времени отправки Wi-Fi списка
  - валидация длины входного SSID (защита от overflow)
- В `App.js` убрать каскад reconnect и сделать единый lifecycle BLE-состояний:
  - `idle -> scanning -> connecting -> discovering -> ready -> error/retry`
- Добавить ограниченный retry с backoff и явным таймаутом.

Критерий готовности:
- 20 последовательных connect/disconnect циклов без зависания UI и без «вечного» reconnect-loop.

## Фаза 2. Новый протокол команды (до миграции UI)
- Перейти от «сырой строки» к структурированному payload, например JSON-lite:
  - `{"v":1,"cmd":"start","ssid":"...","durationMin":3,"dot":true}`
  - `{"v":1,"cmd":"stop"}`
- На firmware добавить ACK/NACK notify:
  - `ok:start`, `ok:stop`, `err:invalid_payload`, `err:ssid_too_long`.
- Добавить совместимость на переходный период (старый формат + новый).

Критерий готовности:
- Приложение получает подтверждение команды и показывает оператору корректный статус устройства.

## Фаза 3. Рефактор текущего React-клиента (под миграцию)
- Вынести BLE в отдельный модуль `src/services/ble/*`.
- Вынести бизнес-логику «старт/стоп/таймер/режим card|word» в отдельный use-case слой.
- Дедуплицировать страницы: общий шаблон + theme/config вместо копипасты 6 файлов.

Критерий готовности:
- UI слой не содержит прямых вызовов GATT, только события/команды в сервис.

## Фаза 4. Переезд на React Native Expo
- Создать Expo-проект и перенести дизайн-систему экранов.
- Подключить нативный BLE пакет для Expo (Android + iOS) и реализовать тот же BLE service API, что в web-рефакторе.
- Перенести настройки с `localStorage` на `AsyncStorage` + схема миграций.

Критерий готовности:
- На целевых устройствах (минимум 2 Android + 1 iOS) выполняются: pairing/connect/start/stop/reconnect.

## Фаза 5. Надежность и полевые тесты
- Стенд тесты с реальным ESP32 + батарейным питанием 18650:
  - холодный старт
  - потеря связи и восстановление
  - серия быстрых команд start/stop
  - длительная сессия 30-60 минут
- Добавить watchdog/heartbeat между app и firmware.

Критерий готовности:
- Подтвержденная стабильная демонстрация без ручных рестартов в течение целевой длительности выступления.

## Фаза 6. Релиз и сопровождение
- Release checklist: версии прошивки и app совместимы по протоколу.
- Обновление AGENTS.md после каждого значимого архитектурного изменения.
- Подготовить «операторский» гайд на 1 страницу (до выступления/во время/аварийный сценарий).

Критерий готовности:
- Повторяемый релиз-процесс и понятная эксплуатация без участия разработчика.

## Приоритеты по вашим текущим болям
1. Сначала стабилизация BLE и новый принцип коннекта (Фазы 1-2).
2. Затем перенос архитектуры клиента (Фаза 3).
3. После этого полноценный Expo-переезд (Фаза 4).

## Ближайший спринт (текущий фокус)
1. Подключить реальный BLE-слой в `mobile/src/services/ble/bleService.js`.
2. Перенести UUID/контракт в единый protocol config.
3. Сделать handshake + статус соединения + retry policy на мобильном клиенте.
4. После этого править прошивку под новый протокол v1 (ACK/NACK и валидация payload).

## Риски
- Ограничения BLE в Web останутся даже после рефакторинга (поэтому Expo migration важна).
- Несовместимость старой и новой прошивки без версии протокола.
- Дублированный UI-код усложняет параллельную разработку, пока не сделана дедупликация.
